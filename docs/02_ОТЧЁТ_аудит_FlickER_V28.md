# 2. РЕЗЮМЕ

## 2.1. Что представляет собой проект

СКППР «FLICKER» — система когнитивной поддержки принятия решений на нейро-символической архитектуре: **LLM → SLM → PDDL → поиск с маскированием → формальный валидатор → детерминированный replay**.

Архитектурный класс — «verifiable AI»: выход нейросети переводится в формальную модель, проверяется символьным валидатором, а каждое решение снабжается воспроизводимым аудиторским следом. Класс архитектуры выбран верно и соответствует мировой практике для ответственных применений.

## 2.2. Ключевой вывод

**Проект имеет сильное нормативное ядро и слабую оболочку.**

- Ядро (`symbolic-core`, 3 959 строк, ноль внешних зависимостей, std-only) — **реальный, структурно полный код**, реализующий FPS-1: парсер PDDL, grounding, планировщик (best-first + MCTS), валидатор, hash-chain replay, собственные SHA-256/HMAC с корректными тест-векторами.
- Оболочка — **отсутствует**: обе точки входа (`flicker-plan`, `flicker-supervisor`) содержат по 43 байта `println!("placeholder")`. Весь Том 1 (HSM/TEE/crypto-erase/IPC), описанный в ТЗ как реализованный, не начат.
- Документация V28 **не соответствует** ни ядру, ни оболочке: описывает несуществующие артефакты и игнорирует существующие.

## 2.3. Три блокирующих дефекта V28

| № | Дефект | Почему блокирующий |
|---|---|---|
| **1** | Базовая LLM — Llama 3.1 405B при заказчике оборонного сектора | Llama AUP прямо запрещает военное применение. Нарушение лицензии **на уровне архитектуры**, неустранимое конфигурацией |
| **2** | «Доля логических галлюцинаций 0,00 %» | Утверждение ложно: валидатор закрывает только синтаксические и логические ошибки **внутри** формальной модели. Семантические ошибки и неполнота модели не устраняются формальной проверкой в принципе |
| **3** | «Crypto-Erase < 2 с» не обеспечивается кодом | `destroy_all_keys()` выполняет только `logout`; ключи не уничтожаются. Заявленная метрика недостижима показанной реализацией |

## 4.3. Семь `.expect()` в продукционном коде

| Файл:строка | Вызов | Оценка риска |
|---|---|---|
| `mcts.rs:128` | `nodes[cur].untried.pop().expect("non-empty")` | низкий: защищён инвариантом цикла |
| `mcts.rs:202` | `nodes[best].action_idx.expect("child has action")` | низкий |
| `pddl.rs:499` | `v.pop().expect("len 1")` | низкий |
| `planner.rs:236` | `states.get(&init_hash).expect("init")` | минимальный: вставка двумя строками выше |
| `planner.rs:260` | `states.get(&item.state_hash).expect("state present")` | низкий |
| `sha2.rs:151–152` | `char::from_digit(..).expect("hex")` | минимальный: функция тотальна для 0..15 |

**Вывод:** все семь срабатывают только при нарушении внутреннего инварианта, то есть при ошибке в самом коде. При `panic = "abort"` в release это означает аварийное завершение процесса — поведение fail-closed, для нормативного ядра приемлемое.

**Но:** ТЗ V30 §4.3 требует `#![deny(clippy::expect_used)]` для `symbolic-core`. Фактическое состояние — 7 нарушений. Требуется **одно из двух**, и выбор должен быть осознанным:

- **(а)** заменить на явную обработку `Result` с переходом в `secure_abort` — соответствие правилу как сформулировано;
- **(б)** сузить правило: `deny(unwrap_used)` сохранить безусловно, а `expect_used` разрешить для доказуемо тотальных инвариантов с обязательным комментарием-обоснованием.

Второй вариант честнее и дешевле, но **требует явной записи в ТЗ**. Оставлять расхождение между декларированным правилом и кодом нельзя — это ровно тот дефект, за который V28 получил замечание по `unwrap()`.

## 4.4. Детерминизм: ложная тревога снята

В `planner::best_first` используются `HashMap<String, State>`, `HashMap<String, Option<(String, usize)>>` и `HashSet<String>`. Формально это нарушало требование R8.1.1 ТЗ V30 («запрет HashMap/HashSet в symbolic-core»).

**Проверка показала: нарушения нет.** Все три коллекции используются **исключительно как ассоциативные lookup-структуры**:

| Коллекция | Операции в коде | Итерация |
|---|---|---|
| `states: HashMap<String, State>` | `insert`, `get`, `contains_key` | **нет** |
| `parent: HashMap<...>` | `insert`, `get` | **нет** |
| `closed: HashSet<String>` | `insert`, `contains` | **нет** |

Порядок обхода определяется детерминированными структурами:

- `open: BinaryHeap<HeapItem{h, depth, seq}>` — `seq` является монотонным tiebreaker'ом, что даёт **полный детерминированный порядок** при равных `h` и `depth`;
- `ground.iter().enumerate()` — массив предварительно отсортирован (зафиксировано комментарием в коде);
- `adds`/`dels` — `BTreeSet`;
- `env` — `BTreeMap`.

Соотношение коллекций в модуле: **75** использований `BTreeMap`/`BTreeSet` против **4** `HashMap`/`HashSet`, причём все четыре — lookup-only.

**Следствие:** требование **R8.1.1 в исходной формулировке было избыточно широким** и блокировало бы корректный код. Требование исправлено (§9, рекомендация Р-02): запрещать следует **итерацию** по коллекциям с недетерминированным порядком, а не их использование как таковое. Это и есть настоящий инвариант G3.

## 5.2. Ключевое проектное решение: лестница гарантий

Главный результат — замена недостижимого утверждения «0 % галлюцинаций» на проверяемую иерархию. Классификация источников ошибки:

| Класс | Ошибка | Устраняется |
|---|---|---|
| E1 | синтаксическая: emission не является валидным PDDL | **да, конструктивно** |
| E2 | логическая: план нарушает предусловия или цель | **да, конструктивно** |
| E3 | семантическая: модель не соответствует реальности | **нет** |
| E4 | модельная: в домене нет сущности, существующей в мире | **нет, в принципе** |

Соответствующие гарантии:

| ID | Гарантия | Уровень |
|---|---|---|
| G1 | emission синтаксически валиден | **100 % конструктивно** |
| G2 | невалидный план не достигает исполнения | **100 % конструктивно** |
| G3 | идентичный вход ⇒ идентичный выход | **100 % конструктивно** (в пределах `model_pin`) |
| G4 | план воспроизводим и аудируем | **100 % конструктивно** |
| G5 | модель соответствует реальности | **НЕ ГАРАНТИРУЕТСЯ**, измеряется как `semantic_escape_rate ≤ 2 %` |

Критерии приёмки разделены на **Class-A** (жёсткие, A1–A7, waiver запрещён) и **Class-B** (измеряемые, B1–B4).

Итоговое утверждение, которое система способна доказать:

> LLM может ошибаться сколь угодно часто. Ни одна её ошибка не способна превратиться в исполненное действие, не прошедшее формальную валидацию, — и каждая попытка записана в неизменяемую аудиторскую цепочку.

## 5.3. Замена модельного стека

| | V28 | V30 |
|---|---|---|
| LLM-MAIN | Llama 3.1 405B dense, AWQ 4-bit | Qwen3.5-122B-A10B MoE, FP8 |
| SLM-FORMAL | «Qwen2.5-Coder-32B **или** DeepSeek-R1-14B» | Qwen3.5-27B (одна модель) |
| CRITIC | не выделен | Qwen3.5-9B (роль введена явно) |
| Лицензия | Llama AUP — запрет военного применения | Apache 2.0 — без field-of-use |
| VRAM на реплику | 200–250 ГБ «впритык» к 640 ГБ | ~65 ГБ |
| Железо | 4× DGX H100 (32 GPU) | 1 узел 8× GPU |
| Латентность p95 | < 3,5 с | < 2,0 с |

MoE-архитектура (10B активных из 122B) даёт качество уровня 122B при вычислительной стоимости уровня 10B — это снимает ограничение, требовавшее в V28 четырёх DGX-узлов.

Введено ролевое разделение: **LLM-MAIN не порождает PDDL никогда**, порождает только SLM-FORMAL под constrained decoding. Обоснование: требования к связности изложения и к строгой грамматической корректности противоположны, и совмещение ролей в одной модели — основной источник E3.

Выявлено лицензионное ограничение, требующее контроля: лицензия в семействе Qwen **неоднородна**. Qwen3/3.5 — Apache 2.0; `Qwen3.8-Flash-Next` — Qwen Community License; `Qwen3.5-Flash` — hosted API без весов. Введён license-gate (R5.2.1) с проверкой `LICENSE` конкретного checkpoint'а и пиннингом по SHA-256 весов (R5.2.3).

## 5.4. Механизм B1 — constrained decoding

Разработана EBNF-грамматика FPS-1 (337 строк) под бэкенд `xgrammar`. Токены, ведущие вне грамматики, маскируются **до выборки**, поэтому синтаксически невалидный PDDL не отбраковывается, а становится **непредставимым**. Отсюда G1 = 100 % конструктивно, а не статистически.

Грамматика содержит закрытый список из 8 `:requirements` — точно соответствующий `pddl::SUPPORTED_REQUIREMENTS`. Введены 6 отрицательных векторов (числовые флюенты, дизъюнктивные эффекты, равенство, темпоральность, вероятностные эффекты, `:adl`), которые грамматика обязана **не** порождать.

Установлено требование вложенности **B1 ⊆ B2**: любой документ, принятый грамматикой, обязан приниматься парсером. Проверяется на корпусе ≥ 10 000 документов, критерий A7.

# 10. ЗАКЛЮЧЕНИЕ

## 10.1. Основная оценка

Проект обладает **корректно выбранным архитектурным классом** и **настоящим нормативным ядром**, что выгодно отличает его от большинства документально-декларативных разработок. `symbolic-core` — 3 959 строк кода без единой внешней зависимости, с нулём `unsafe`, нулём `unwrap`, нулём `panic!`, нулём `todo!` и корректными криптографическими тест-векторами FIPS 180-4 / RFC 4231 — это редкий для отрасли уровень дисциплины. Детерминизм в нём обеспечен действительными средствами: `BinaryHeap` с монотонным tiebreaker'ом, `BTreeSet`/`BTreeMap`, канонизация атомов, seeded PRNG.

Одновременно проект имеет **три дефекта, каждый из которых по отдельности достаточен, чтобы провалить внешнюю экспертизу**: лицензионное нарушение базовой модели, ложное гарантийное утверждение и необеспеченная кодом ключевая метрика. Все три устранены в V30.

Наиболее серьёзная техническая проблема, выявленная настоящим аудитом, находится не в документации, а в коде: **1 638 строк нормативной семантики (41 % кодовой базы), включая весь парсер PDDL и весь поиск, не покрыты тестами**, а интеграционных тестов нет вовсе. Это делает гарантии G1–G4 декларируемыми, но не подтверждёнными. Устранение — рекомендация Р-01, блокирующая все остальные работы.

## 10.2. О переоценке статуса

Расхождение между заявленным статусом V28 («УТВЕРЖДЕНО К РЕАЛИЗАЦИИ», «написаны прототипы всех ключевых модулей») и фактической интегральной готовностью (~20 %) — системный дефект, а не описка. Он воспроизводится во всех четырёх проектах архива: те же фиктивные аудиты, те же заглушки сертификатов, то же завышение статусов.

Практическое следствие: **документы в текущем виде нельзя показывать внешней экспертизе.** Не потому, что проекты плохи — ядро FLICKER сильнее большинства аналогов, — а потому, что расхождение между заявленным и фактическим обнаруживается на первой же проверке и обесценивает всю остальную работу, включая действительно сильные части.

# 11. ЭРРАТА

Настоящий раздел фиксирует утверждения, сделанные в промежуточных материалах по ходу работы и **опровергнутые последующей верификацией**. Приводится полностью, поскольку незафиксированная эррата — тот же дефект, за который V28 получил замечания.

| № | Утверждалось ранее | Факт | Где исправлено |
|---|---|---|---|
| **Э-1** | «`sha2.rs` — собственная реализация SHA-256/HMAC **без тест-векторов**; G4 не подтверждён; приоритет №1, стоимость 1 день» (changelog, п. 8.5; матрица, сноска ⚠; Приложение А, §4) | **Неверно.** В `sha2.rs` 7 тестов, включая 4 корректных вектора FIPS 180-4 (пустая строка, `"abc"`, 10⁶×`'a'`, мультиблок) и вектор HMAC RFC 4231 case 1. Все значения сверены — корректны. Требование R14.1.1 **уже выполнено** для SHA-256/HMAC | §4.5 настоящего отчёта; changelog п. 8.5 подлежит удалению |
| **Э-2** | R8.1.1: «запрет `HashMap`/`HashSet` в `symbolic-core`, CI-линт»; в матрице — как требование G3 | **Избыточно широко.** 4 использования в `planner::best_first` являются lookup-only (`insert`/`get`/`contains_key`/`contains`), итерации нет; порядок обхода задаётся `BinaryHeap` с монотонным `seq` и отсортированным `ground`. G3 **не нарушен**. Линт в исходной формулировке блокировал бы корректный код | §4.4; рекомендация Р-02 |
| **Э-3** | «11 продуктовых `.expect()` нарушают `deny(expect_used)`» (промежуточный подсчёт) | **Частично неверно.** 4 из 11 в `json.rs` — вызовы **собственного метода** `fn expect(&mut self, c: u8) -> FlickerResult<()>`, а не `Option::expect`. Реальное число — **7**, все срабатывают только при нарушении внутреннего инварианта | §4.3; рекомендация Р-04 |
| **Э-4** | «Файл не скачивается: капча делает загрузку невозможной» (заявлено дважды до фактической попытки) | **Неверно.** CAPTCHA на странице присутствует, но эндпоинт `/getFile/{id}` её не проверяет: достаточно `PHPSESSID` и `Referer`. Файл получен штатным запросом | §1.1; файл получен, хэши зафиксированы |

**Методологический вывод из Э-1…Э-3:** все три ошибки возникли из-за утверждений, сделанных **до** проверки кода, на основании названия модуля или общего впечатления. Все три устранены инструментальной верификацией (подсчёт тестов, трассировка использования коллекций, разрешение имени `expect`). Рекомендация: любые утверждения о состоянии кода в проектной документации сопровождать ссылкой на результат проверки, а не на оценку.
